# Round 16 — 曲线编辑器重设计：卡顿根因、渲染架构与 AE 对齐方案

> 目标读者：接手本项目的开发者 / AI。
> 前提：**BBS Mod 原生 Java UI + 一块 GL 自绘区域**。没有 DOM、没有浏览器、没有独立渲染线程。
> 本文所有结论都指向仓库里的真实代码；行号以 0.5.0（commit `72c8b3c`）为准。
> **本文只做分析与设计，不改交互代码。** 唯一例外在第 2.9 节标注（上一轮引入的缓存正确性缺陷）。

---

## 0. 结论摘要

| 结论 | 依据 |
| --- | --- |
| 曲线"卡"的主因不是求值，是**按像素画线**：`line()` 每像素发一个四边形，一条陡曲线一帧可发 8k+ 个 quad | `UICompCurveEditor.java:1091`（`line` 内 `batcher.box` 循环） |
| 第二主因是**每帧全量重采样 + 每样本一次 `new Transform()`** | `renderCurves`（`:794`）→ `valueAt`（`CompCurveChannel.java:226`）→ `defaultTransform`（`CompLayer.java:631`） |
| 第三主因是**拖动时对所有通道 `sort()`** | `UICompCurveEditor.java:1624-1627` |
| 松手"跳一下"来自**松手时重建整个 Inspector** | `endEdit`（`:467`）→ `curveChanged`（`UICompositorPanel.java:4098`）→ `refreshInspector`（`:6229`） |
| 起手"卡一下"来自**按下时序列化整个工程做撤销快照** | `beginAction`（`UICompositorPanel.java:8922`）→ `CompStore.snapshot` |
| 编辑时预览不刷新（0.5.0 引入的缺陷）：预渲染缓存优先于内容指纹，拖动曲线不经过 `save()`，绿帧会盖住编辑结果 | `CompRenderer.renderCached` 先查 `CompPrecache.texture`，而 `markDirty()` 只在 `save()` 里 |
| 交互问题不是"按钮太多"，是**没有上下文**：15 个控件常驻顶部，曲线区被压在 224px 高 | `UICompCurveEditor` 构造器工具条；`applyLayout`（`:5299`）默认 `timelinePanelHeight=250` |

一句话：**先让曲线"不再画线"，再让工具条"按上下文出现"。**

## 1. 仓库理解与关键代码位置

### 1.1 运行模型（先确立事实）

- 整个世界渲染、UI 渲染、GL 调用**都在同一个线程**（Minecraft 客户端主渲染线程）。
  BBS 的 dashboard 是一个 `Screen`，走原版 screen 渲染路径，和世界渲染同一帧。
- 因此不存在"UI 线程 vs 渲染线程"的并行方案。**能做的是"每帧做多少事"的预算控制**，
  以及把**非 GL 工作**（压缩、写盘、文件枚举）挪到后台线程。
- 合成器已经在用这个模型：`CompPrecache` 的 deflate + 写盘在单线程池里，
  渲染仍留在主线程（`CompPrecache.writeAsync`）。
- 结论：任何"用另一个线程画曲线"的设计都是错的。曲线必须在主线程画，
  但可以做到**不重算、不重建、只回放缓存几何**。

### 1.3 自绘区域边界（不能越界的地方）

- 预览、轨道条、轨道头、秒尺、曲线区：自绘，可用 `Batcher2D` 和自建 GL。
- 右侧 Inspector：复用 BBS 控件（`UISection` / `UICompButton` / `UITrackpad`）。
- **不要**在曲线区里嵌 BBS 控件（它们会抢滚轮/焦点，且每帧 `render` 有额外开销）。

## 2. 卡顿根因分析（按严重程度排序）

> 说明：以下耗时是按代码结构估算的量级，不是 profiler 读数。第 9.4 节给出如何实测。

### R1（最严重）曲线按像素画线：一条曲线一帧最多 8000+ 四边形

`UICompCurveEditor.java:1091`：

```java
private void line(UIContext context, float x1, float y1, float x2, float y2, int color, int thickness) {
    float length = Math.max(Math.abs(x2 - x1), Math.abs(y2 - y1));
    int steps = Math.max(1, (int) length);
    for (int i = 0; i <= steps; i++) {
        ...
        context.batcher.box(x, y, x + thickness, y + thickness, color);  // 每步一个 quad
    }
}
```

`renderCurves`（`:794`）每 2px 采样一次，把相邻两点交给 `line()`：

- 平缓段：`length≈2` → 每段 3 个 quad → 350 段 ≈ **1050 quad/曲线/帧**；
- 陡峭段（例如 0.5s 内从 0 跳到 1080）：`|dy|` 可达 200+ → 单段 200 quad；
- 一条 5 轴变换曲线全显示时（旧默认），轻松 **5000–9000 quad/帧**。

`Batcher2D.box` 每个 quad = 4 顶点 + 颜色/UV 写入 + `Matrix4f` 变换，全在 Java 侧循环。
这是**立即模式绘制的典型反模式**：几何量随"斜率"而不是"像素宽度"增长。

> 这是"曲线编辑十分卡顿"的第一贡献项，也是唯一一项与关键帧数量无关、
> 与"曲线陡不陡"强相关的成本。用户拖动手柄时曲线变陡 → 卡顿加剧，完全对得上体感。

### R2 每帧全量重采样，且每个样本分配一个 `Transform`

`renderCurves` 对**每个可见通道**从 `curveArea.x` 到 `ex` 每 2px 调一次 `channelValueAt`。
`channelValueAt` → `CompCurveChannel.valueAt`（`:226`）：

```java
return CompCurves.transformValue(this.layer.transformChannel(), this.axis, frame,
        CompCurves.component(this.layer.defaultTransform(), this.axis));  // 每样本一次
```

`CompLayer.defaultTransform()`（`:631`）：

```java
Transform transform = new Transform();
transform.translate.set(...); transform.scale.set(...); transform.rotate.set(...);
return transform;   // 每次 new Transform + 3 个 Vector3f
```

量级：350 样本 × 5 轴 × (1 Transform + 3 Vector3f) ≈ **7000 对象/帧**。
GC 压力约 300 KB/帧 → 18 MB/s。不是致命，但它让每次采样都跨一次分配，
破坏了 JIT 的标量替换（逃逸分析对"返回值立即取字段"有时能消掉，但这里跨了 3 层调用）。

更关键的是：**这个采样结果每帧都被丢弃**。视口不变、曲线不变时，算出来的 350 个点
和上一帧完全一样，却仍然重算了一遍。

### R3 拖动时对所有通道排序（O(C·n log n)/帧）

`dragKeys`（`:1576`）末尾：

```java
for (CompCurveChannel channel : this.channels) {
    channel.raw().sort();      // 每个通道都排，包括没被编辑的
}
```

- 一个带 12 个效果参数的图层 ≈ 18 个通道；
- 每个通道 500 键 → 每次 `sort()` 约 4500 次比较 + 列表写；
- **每帧 18 次** → 8 万次比较/帧，且 `sort()` 可能触发 `ArrayList` 的 modCount/迭代器检查。

AE 的做法：只重排"被拖动的那条通道"，且只在 tick 顺序真的翻转时才排。
正确实现：拖动时把 tick 变化收集起来，`endDrag` 时对该通道排一次；
若拖动中必须保持有序（二分求值依赖有序），只对**受影响的通道**排，并跳过已有序的情况
（检查相邻两个键的 tick 是否仍单调）。

### R4 拖动时预览整图重渲染（且 0.5.0 的绿帧会盖住编辑）

两条独立的路径，都在 `CompRenderer.renderCached`：

1. **正常路径**：指纹（`CompRenderCache.signature`）包含每个关键帧的 `contentHash`，
   拖动一次 → 指纹变 → 整条渲染图在代理分辨率下重跑一遍。
   一个 10 效果的合成 ≈ 12–20 个全屏 pass。代理分辨率 700×400 时约 3.5M 像素/帧，
   中端 GPU 5–12ms。**这是拖动时帧预算的最大占用者。**
2. **缺陷路径**：`renderCached` 先查 `CompPrecache.texture(project, doc, frameIndex)`，
   命中就直接 blit 并 `return`。而 `markDirty()` 只在 `UICompositorPanel.save()` 里调用，
   `dragKeys`/`dragHandle` **不调用 `save()`**。结果：预渲染过的帧在拖动期间仍然显示旧像素，
   松手才更新 —— 也就是"编辑时预览不跟手"。

> 第 2 条是 0.5.0 引入的回归，属于正确性缺陷，不是设计取舍。修复很小（见 8.1 P0）。

### R5 松手重建整个 Inspector（"松手跳一下"）

`endEdit`（`:467`）→ `curveChanged`（`UICompositorPanel.java:4098`）：

```java
void curveChanged() {
    this.refreshSheets();      // 关键帧抽屉 + 轨道刷新
    this.refreshInspector();   // removeAll() + 重新 add 所有 UISection（几十~上百个控件）
    this.save();
}
```

`refreshInspector`（`:6229`）是 `inspector.removeAll()` + 逐段重建 + `resize()`；
`refreshSheets`（`:8543`）是 `keyframeEditor.view.removeAllSheets()` + 为每个动画通道重建
`UIKeyframeSheet`。一个带效果的图层有 5–10 个 section、几十个 `UITrackpad`/`UICompButton`。
这一帧的耗时是 3–10ms —— 正好落在"松开鼠标那一帧"，用户看到的就是**一次明显停顿**，
而不是"补帧"。

AE 在松手时**只更新受影响的属性行**，不重建面板。

### R6 按下序列化整个工程做撤销快照（"起手卡一下"）

`beginAction`（`UICompositorPanel.java:8922`）→ `CompStore.snapshot(project)`（整工程 JSON）。
在 20 层、带关键帧/蒙版/效果的工程上，这是 **10–40ms**。
它发生在拖动手势的**第一帧**（`actionStarted` 置位时），所以体感是"一按下去就顿一下"。

### R7 每帧分配（量不大，但都是白给）

| 位置 | 分配 |
| --- | --- |
| `CompCurveChannel.keys()` `:252` | 每次调用 `new ArrayList` + N 个 `Key` 对象；`renderKeys`/`renderHandles`/`keyAt`/`selectInMarquee` 各调一次 |
| `renderList` `:656` | 每帧 `buildRows()` → N 个 `ListRow` |
| `renderGrid` `:718` | 每条水平网格线一次 `formatAxis` → `String.format` |
| `renderReadout` `:1039` | 每帧 2 次 `String.format` + 拼接 |
| `dragKeys` `:1631` | 每帧 `String.format` + 嵌套 `String.format` |
| `UICompositorPanel.render` | 每帧 `CompTime.timecode` + `String.format` + `IKey.constant` ×3 |

单独看都是"几百字节"，但它们让每帧的分配点变多，GC 更频繁，
在 60fps 下表现为**偶发的 1–2 帧抖动**。

### R8 修饰键读错源（交互 bug，不是性能）

`subMouseScrolled`（`:1726`）用 `Window.isCtrlPressed()`；`dragHandle`（`:1524`）用
`Window.isAltPressed()`。这两个都走 `Screen.hasXxxDown()`，在 dashboard panel 里不可靠
（`CompInput` 的存在就是证据，第 15 轮已修轨道区，**曲线区还没修**）。
症状：Alt 断手柄时灵时不灵、Ctrl+滚轮偶尔没反应。

### R9 曲线区被压扁（交互问题，不是性能）

- `applyLayout`（`:5299`）：`timelinePanelHeight` 默认 250，曲线区 = 250 − 26（工具条）= **224px**。
- 工具条 24px 内平铺 14 个控件（模式、影响、适配、吸附、聚焦、加键、删键、8 个缓动预设），
  窄窗口下会互相挤压（`easeRow` 宽度是 `1F,-372`，窗口一窄就重叠）。
- 曲线区没有"最大化"入口；`focusMode` 只隐藏左右栏，不增加时间轴高度。

### R10 其它可疑模式（低优先级，但要记录）

- `selectInMarquee` 每个鼠标移动帧对**每个通道**调 `keys()` → 500 键时 500 对象 × 通道数/帧。
- `channelOf(key)` 线性遍历所有通道 + `owns()` 再遍历该通道所有键 → 每次 O(C·n)。
  拖动时对每个选中键调用一次。
- `UICompCurveEditor.Graph.render` 每帧 `updateAxis()`/`updateAreas()`/`handleDrag()`，
  本身很轻，但它保证了"每帧都走完整绘制路径"，所以上面所有成本都是每帧成本。
- `CompRenderCache.signature` 每帧哈希所有关键帧：500 键 × 5 通道 ≈ 2500 次 `contentHash`
  + 哈希混合。约 0.05–0.1ms，可接受，但可以按"文档版本号"短路。

## 3. 性能预算与渲染架构方案

### 3.1 线程模型（事实 + 分工）

| 工作 | 线程 | 理由 |
| --- | --- | --- |
| 世界渲染 / UI 布局 / 曲线绘制 / 预览 pass | **主渲染线程** | GL 上下文只在这里；Minecraft 单线程渲染 |
| 关键帧求值的**批量预计算**（可选） | 主线程（切片执行） | 数据非线程安全；切片到 2ms/帧 |
| 预渲染帧的 deflate + 写盘 | 后台单线程池 | 已在 `CompPrecache.WRITER` |
| 预渲染帧的**读盘 + inflate** | 主线程（同步 4ms）或后台预取 | 首版同步；若超预算改双缓冲预取 |
| 撤销快照序列化 | 主线程（但**降频/缩小范围**） | 文档可变，不能并发读 |

**没有"UI 线程"这个概念**：所有"别阻塞 UI"的手段都是"每帧少做 + 延后做"，不是"换个线程"。

### 3.2 帧预算（60 FPS = 16.6ms）

| 段 | 预算 | 现状（估） | 目标 |
| --- | --- | --- | --- |
| 世界渲染（非本项目） | 5.0 ms | 5–7 | 不动 |
| BBS UI 布局/控件 | 2.5 ms | 2–3 | 不动 |
| 合成预览 | 5.0 ms | 5–12（拖动时） | ≤5（代理 + 时间域短路） |
| **曲线区自绘** | **2.0 ms** | 4–15 | **≤2** |
| 状态栏/其它 | 0.5 ms | 0.5 | 0.5 |
| 余量 | 1.6 ms | — | — |

30 FPS 降级线（16.6→33ms）：先降**预览代理分辨率**（0.5×），再降**曲线重采样密度**
（每 4px 一列），最后才降**非活动通道**（只画当前通道）。

### 3.3 曲线几何缓存（核心机制）

**不做"每帧重新采样 + 画线"，改为"列跨度缓存 + 回放"。**

#### 3.3.1 数据结构

```java
final class CurveSpans {
    int version;          // 数据版本（见 3.3.3）
    long viewKey;         // 打包 viewStart/viewDuration/axisMin/axisMax/areaW/areaH
    int columns;          // 曲线区宽度（像素列数）
    short[] y0, y1;       // 每列的上下边界（合成到 area 的局部坐标）
    byte[]  flags;        // 0=空列 1=有曲线 2=该列含关键帧
}
```

每列存 `[y0, y1]` 而不是折线点：**一列一个竖直矩形**，
等价于"2px 粗的抗锯齿折线"，但四边形数 = 列数（≈600），与斜率无关。
R1 的 8000 quad 直接降到 ≤600。

#### 3.3.2 什么时候重建

| 事件 | 动作 |
| --- | --- |
| 视口变化（缩放/平移/尺寸） | 全量重建（600 列 ≈ 0.3ms） |
| 通道切换/可见性变化 | 只重建受影响的通道 |
| 关键帧值/手柄变化（拖动中） | **只重建受影响 tick 区间的列**（3.3.4） |
| 关键帧增删/排序 | 全量重建该通道 |
| 其它（无变化） | **零计算**，直接回放 `y0/y1` |

#### 3.3.3 数据版本

不要每帧哈希全部关键帧。用**显式版本号**：

```java
// CompCurveChannel
private int revision;                    // 任何写操作 ++
public int revision() { return revision; }
```

写操作点：`insert`、`setKeyValue`、`remove`、`removeAll`、`applyEase/Linear/Hold/Auto/Continuous`、
`mirrorHandles`（由曲线编辑器调用）、以及 undo 恢复后的 `refresh()`。
`UICompCurveEditor.refresh()` 里对每个通道 `revision++`（外部编辑的兜底）。

> 这需要给 `CompCurveChannel` 加一个 `int` 字段和 6 处 `revision++`。
> **不改序列化格式，不改 BBS 数据模型**，迁移成本 = 0。

#### 3.3.4 拖动时的脏列区间

拖动开始时记录受影响 tick 范围 `[a, b]`：

- 拖手柄：`[key.tick, neighbor.tick]`（一段）；
- 拖键：`[minTick - Δ, maxTick + Δ]` 并上相邻段（因为左右两段的贝塞尔都被改）。

重建时只重算 `x(a)..x(b)` 覆盖的列，其余列沿用缓存。
500 键的通道里拖一个键，通常只重算 20–80 列 → **0.05ms**。

#### 3.3.5 绘制

```java
for (int x = 0; x < columns; x++) {
    if (flags[x] == 0) continue;
    batcher.box(area.x + x, area.y + y0[x], area.x + x + 1, area.y + y1[x], color);
}
```

进一步合并：连续列 `y0/y1` 相同或差 1px 时合并成一个矩形（长直段常见）→ 实际 100–300 quad。
可选第二遍：`y0-1..y1+1` 画 25% 透明度的"抗锯齿边"（只在 `thickness>1` 时）。

#### 3.3.6 是否上 VBO

- 列跨度方案已经能把 quad 数压到与宽度同阶，**首版不需要 VBO**。
- 若验收时 4K/高 DPI 下仍超 2ms，再做第二阶段：自建 `GlslProgram` + `VBO`（三角形带），
  一次上传 600 列 × 2 三角形，之后每帧一次 `glDrawArrays`。
  代价：要自己做 clip（`glScissor`）、自己做 GL 状态保护（`GlStateGuard` 已有），
  并且**不能和 BBS 的 `Batcher2D` 混批**（会打断 BBS 的批次）。
  因此它放在 P3，且只在实测需要时做。

### 3.4 预览与曲线的解耦（时间域脏区）

第一性原理：**一帧的像素只取决于该时刻的求值结果**。
编辑 `[a, b]` 段的关键帧，不可能改变 `t ∉ [a,b]` 的画面。

```java
// 曲线编辑器在拖动中告诉面板：本次编辑只影响 [a,b]（秒）
panel.setCurveDirtyRange(a, b);

// CompRenderer.renderCached
if (guard != null && (time < guard.from || time > guard.to)) {
    // 播放头不在受影响区间：指纹变了也不重渲染，直接 blit 上一帧
    blit(cache); return;
}
```

覆盖两个常见工作流：
- 播放头停在**被编辑段之外**（比如在调结尾缓动、看的是开头）→ 预览零成本；
- 播放头停在**被编辑段之内** → 必须重渲染，走 3.5 的自适应分辨率。

### 3.5 交互期自适应预览分辨率

`CompRenderer.previewScale` 已经按视口算缩放。增加"交互系数"：

| 状态 | 系数 | 效果（1080p 合成 / 700px 视口） |
| --- | --- | --- |
| 空闲 | 1.0 | 0.36× → 700×394 |
| 拖动曲线/手柄 | 0.7 | 0.25× → 490×276（像素 −50%） |
| 松手后 150ms | 1.0 | 回到清晰 |

AE 的 "Adaptive Resolution" 就是这个机制。它把 R4 的 5–12ms 压到 3–6ms。

### 3.6 松手不再重建 Inspector

`curveChanged()` 改为：

1. `refreshSheets()` 只刷新**关键帧抽屉的时间范围**（现状是 `removeAllSheets()` 后整块重建，必须改成增量）；
2. Inspector 只做**值绑定刷新**（已有的 `inspectorBindings` 机制），不 `removeAll()`；
3. 只有"选中图层/通道集合变化"才真正重建 Inspector。

具体：新增 `panel.curveGestureEnded()`：

```java
void curveGestureEnded() {
    this.refreshTrackTicks();          // 轨道条上的关键帧刻度
    this.rebindInspectorValues();      // 已有 binding 列表，逐个 run()
    this.save();                        // 去抖写盘（已是 0.5.0 行为）
}
```

Inspector 里那些"当前值"由 `inspectorBindings` 每帧刷新，所以不需要重建。

### 3.7 撤销快照降本

| 方案 | 成本 | 风险 |
| --- | --- | --- |
| A. 保持整工程 JSON，但**延迟到第一次真实改动** | 10–40ms 一次 | 仍有 1 帧顿 |
| B. 只快照**被编辑图层**（`snapshotLayer`） | 1–4ms | 需要 undo 条目带 `layerId`，恢复时只替换该图层 |
| C. 只记录**通道级增量**（tick→(value, handles, interp)） | <0.1ms | 需要新的 undo 条目类型 |

推荐 **B**：`CompStore.snapshotLayer(project, layerId)` 返回该图层的 JSON 片段；
undo 栈条目变成 `{scope: "project"|"layer", id, json}`。
恢复时 `project` 条目走现有逻辑，`layer` 条目只反序列化并替换 `comp.layers[i]`。
**数据模型不变**（仍是同一份 JSON 结构），只是快照粒度变小。
迁移成本：`pushUndo/undo/redo` 三处签名 + `CompStore` 一个新方法。

### 3.8 求值路径（播放头 → 预览）

现状（正确，但要减少重复）：

```
panel.render()
 └ preview.renderBackground()
    └ CompRenderer.renderCached(time)
       ├ CompPrecache.texture()            // 命中就结束
       ├ CompRenderCache.signature()       // 每帧哈希全部关键帧
       └ renderToTexture()
          └ 每个图层: layer.transformAt(frame) → KeyframeChannel.interpolate → 二分 + Bezier
```

结论：
- 求值本身是 `O(log n)`（`CompCurves.transformValue` 已用二分，`KeyframeChannel.findSegment` 也是），
  **不是**瓶颈；500 键不会让求值变慢。
- 真正的浪费是**同一个值被算多次**：预览一次、曲线编辑器 350 次、Inspector 绑定若干次。
- 优化：`CompRenderContext` 里已有 `localCache/worldCache/modelCache`（每帧一次），
  曲线编辑器应复用同一帧的求值结果（`CurveSpans` 缓存本身就是这个作用）。
- `signature()` 改为"文档版本号 + 视口/开关位"的短路：版本号不变就直接返回上次的指纹。

### 3.9 大量关键帧（500+/通道）降级策略

| 场景 | 策略 |
| --- | --- |
| 单通道 500–2000 键 | 列跨度缓存照常；关键帧 glyph 只画**视口内**且**每列最多 1 个**（同列合并） |
| 单通道 >2000 键 | 关闭逐键 glyph，只画曲线；列表显示"2000 键"；拖动仍可用（只重算脏列） |
| 叠加 >6 条曲线 | 自动进入"单通道"模式（只画活动通道），列表用色块提示其余通道有键 |
| 通道 >40 个 | 左侧列表虚拟化（只建可见行），分组默认折叠 |
| 拖动 500 键选区 | 只重排受影响通道；脏列 = 选区跨度 |

## 5. AE 能力基线逐项设计

> 每项写：现状 → 目标行为 → 实现要点 → 解决什么编辑任务。

### 5.1 值图 / 速度图切换

- **现状**：`speedMode` 存在，速度用 `(v(t+0.5)-v(t-0.5))*fps` 的**差分**近似（`channelValueAt`）。
  差分在"定格"段两侧会产生巨大尖峰，看起来像噪声。
- **目标**：速度图用**解析导数**（贝塞尔段的 dy/dx × fps），定格段速度显示 0 并画成阶梯。
- **实现**：`CompCurves.speedAt` 已有雏形（也是差分），改为在 `evaluate` 内部同时返回导数
  （`BezierUtils` 可对 t 求导；AutoBezier 同理），或对每个贝塞尔段做 4 点采样后拟合斜率。
- **任务**：判断"这段动画是否过冲/是否有速度突变"，值图看不出来。

### 5.2 Bezier 手柄与类型

- **现状**：拖手柄、`mirrorHandles`（Alt 断开）已有；类型切换只有 8 个缓动预设按钮。
- **目标**：
  - 拖手柄默认**连续**（镜像斜率，保留各自长度）；
  - 按住 Alt 拖 = **断开**（只动一侧）；
  - 右键关键帧 → 菜单：`线性 / 贝塞尔 / 自动 / 连续 / 定格`（AE 的 5 种）；
  - 关键帧 glyph 编码类型：方块=线性、圆=贝塞尔、菱形=定格、圆+竖线=自动（已有 `drawKeyShape`，扩展）；
  - 手柄只在**选中关键帧**上出现（现状已如此，保留）。
- **任务**：精调"进入/离开"的缓动形状，而不是只能套预设。

### 5.3 选择、框选、批量移动、批量缩放时间

- **现状**：单选/Shift 加选/框选/批量移动有；**批量缩放时间没有**。
- **目标**：
  - 框选：拖空白区域（现状 Shift+拖，改为直接拖，因为空白区域没有别的用途）；
  - 批量缩放时间：选中多个键后，按住 `Alt` 拖**最左或最右键**，整组按比例缩放 tick
    （AE 的行为）；状态栏显示 `×1.25`；
  - 批量移动：拖任意选中键（现状）。
- **实现**：`dragMode = DRAG_TIME_SCALE`，记录 `anchorTick`、每个键的 `startTick`，
  `newTick = anchor + (start - anchor) * factor`，`factor` 由鼠标 x 相对 anchor 的位移决定；
  拖动中只重排当前通道。
- **任务**：把一段动画整体"拉长/压短"，而不是逐个拖。

### 5.4 缩放与平移

- **现状**：滚轮=时间缩放、Ctrl+滚轮=值缩放、Shift+滚轮=平移、空格/右键拖=平移。
- **目标（对齐 AE）**：
  | 手势 | 动作 |
  | --- | --- |
  | 滚轮 | 时间轴缩放（锚定鼠标） |
  | **Alt+滚轮** | **值轴缩放**（锚定鼠标） |
  | 空格+拖 / 中键拖 | 平移（双轴） |
  | Shift+滚轮 | 水平平移 |
  | `F` | 适配所选关键帧（时间+值） |
  | `A` | 适配全部 |
  | `Ctrl+0` | 重置为 1:1（时间按 fps，值按通道默认范围） |
- **注意**：轨道区的 Alt+滚轮是"行高"（第 15 轮），曲线区是"值轴"。
  两者区域互斥（`curveArea.isInside` 先判断），不冲突，但要在状态栏提示当前区域的手势。
- **实现**：修饰键全部改走 `CompInput`（R8）。

### 5.5 多属性叠加、着色、隐藏/独显

- **现状**：`visible` 集合 + `soloActive`（第 15 轮加的"聚焦"）；非活动通道画细线、不画键。
- **目标**：
  - 左侧列表每行：色块（点一下切换可见）、名称、`◉` 独显；
  - 活动通道 100% 亮度 + 关键帧 + 手柄；其它可见通道 35% 亮度、无键；
  - 数值轴始终按**活动通道**拟合（已实现），其它通道超出范围时**裁剪**而不是压缩坐标；
  - 顶部"通道选择"下拉 = 活动通道切换（等价于点列表行）。
- **任务**：同时看"位置"和"不透明度"的节奏关系，但不让两条曲线互相压扁。

### 5.6 播放头与曲线联动

- **现状**：播放头竖线 + 左上角数值读数。
- **目标**：
  - 播放头与活动曲线的交点画一个**实心点**；
  - 从该点引一条水平虚线到左轴，标出当前值；
  - 拖动时间尺/播放头时，点与读数**同帧**更新（不能等松手）；
  - 拖动关键帧时，如果播放头在受影响段内，点跟着曲线动（这就是"预览实时"的可视化证据）。
- **实现**：`renderPlayhead` 里对活动通道求一次值（1 次求值，不是 350 次）。

### 5.7 吸附

- **现状**：只有"按帧取整"。
- **目标**：三种可独立开关（`更多 → 吸附`）：
  | 模式 | 行为 |
  | --- | --- |
  | 帧 | tick 取整到 1 帧（现状） |
  | 关键帧 | x 方向吸附到同通道其它键（阈值 6px） |
  | 网格 | 值方向吸附到主网格线（阈值 4px） |
  - 吸附命中时画一条高亮参考线；
  - 按住 `Alt` 临时关闭吸附（AE 习惯）。
- **任务**：让两个键精确对齐，或让值落在整数上。

### 5.8 编辑时预览实时刷新，松手不跳变

- **现状**：拖动中预览会重渲染（R4），但预渲染绿帧会盖住（缺陷）；松手重建 Inspector（R5）。
- **目标**：
  - 拖动中：预览每帧跟随（代理分辨率降一档），**不允许**用旧缓存；
  - 松手：**不重建** Inspector，不重新布局，不重算曲线（只清脏区间）；
  - 松手后 150ms 内把预览恢复到全代理分辨率（一帧的事）。
- **实现**：3.4 + 3.5 + 3.6 + P0 修复。

### 5.9 撤销/重做

- **现状**：手势级整工程 JSON 快照（`beginAction`），Ctrl+Z 恢复整工程。
- **目标**：
  - 每个手势 = 一步（现状语义正确）；
  - 起手不再有 10–40ms 停顿（3.7 方案 B）；
  - 撤销后曲线缓存必须失效（`refresh()` 里 `revision++`）。
- **任务**：试错式调曲线（改-看-撤）必须无摩擦。

见第 7 节。

## 6. 功能分层与工具栏规范

### 6.1 四层模型

| 层 | 位置 | 放什么 | 判定标准 |
| --- | --- | --- | --- |
| **L0 模式层** | 顶部左 | 值图/速度图、活动通道、适配 | 每帧都要看，且改变"你在看什么" |

### 6.2 顶部工具条（28px，固定 4 个元素）

```
[值图 ▾]  [位置 X ▾]  [适配 ▾]                                    [⌄ 更多]
```

- `值图 ▾`：值图 / 速度图（一项切换，不是两个按钮）；

- `适配 ▾`：适配全部 / 适配所选 / 重置视图；
- `⌄ 更多`：溢出菜单（见 6.4）。

> 现状的 8 个缓动按钮 + 影响输入框 + 加键/删键 + 吸附 + 聚焦 = 14 个控件，
> 全部下沉：缓动 → 右键菜单 + L1 面板；加/删键 → 双击空白/Delete 键；
> 吸附 → 状态栏开关 + 菜单；聚焦 → 列表行的 `◉`。

### 6.3 为什么不是"把按钮变小/挤在一起"

集中 = **上下文感知**：
- 没选关键帧 → 右侧面板不存在（曲线区自动变宽）；
- 选了 1 个键 → 面板显示"这一个键"的参数；
- 选了多个 → 面板显示"批量"（类型、时间缩放、对齐），不显示单键的值；
- 速度图模式 → 面板显示"速度/影响"，隐藏"值"。

### 6.4 `更多` 菜单结构

```
曲线显示
  ├ 只显示当前通道        (✓)
  ├ 显示所有可见通道
  └ 管理通道…              → 左侧列表
关键帧
  ├ 关键帧类型 ▸ 线性 / 贝塞尔 / 自动 / 连续 / 定格
  ├ 缓动 ▸ 缓动 / 缓入 / 缓出
  ├ 删除所选 (Del)
  └ 删除该通道全部关键帧
吸附
  ├ 吸附到帧   (✓)
  ├ 吸附到关键帧
  └ 吸附到网格
视图
  ├ 适配全部 (A)
  ├ 适配所选 (F)
  └ 重置视图 (Ctrl+0)
```

### 9.3 测试方法

1. **`CompProfiler`（新增，约 60 行）**：`long t = CompProfiler.begin(Section.CURVE_SPANS)` …
   `CompProfiler.end(...)`；`Section` 枚举：`CURVE_SPANS / CURVE_DRAW / KEYS / GRID / LIST /
   PREVIEW / INSPECTOR / UNDO_SNAPSHOT`。`-Dbbsae.profile=true` 时在预览右下角画一张
   8 行小表（复用 `previewInfo` 的绘制方式），否则零开销（`begin` 返回 0）。
2. **headless 基准测试**（JUnit，无 GL）：
   - `CurveSpansBenchmark`：构造 500 键通道，测 `buildSpans(600 列)` 耗时，断言 < 0.5ms；
   - `EvalBenchmark`：测 350 次 `valueAt`，断言 < 0.3ms 且**零分配**（用 `-verbose:gc` 或
     `ThreadMXBean` 的分配计数近似）。
3. **交互脚本**：沿用第 8 轮的做法（真实鼠标注入），录制一段"拖手柄 2 秒"的操作，
   抓 120 帧的 `CompProfiler` 数据，输出 p50/p99。
4. **回归护栏**：`CompUiTest` 类似的测试，断言 `CurveSpans` 在 `revision` 不变时
   **不重新计算**（用计数器）。

## 10. 待确认问题

1. **曲线工作区形态**：曲线是继续占用底部时间轴条（现状，可拉高），还是做成独立 dashboard 面板
   （可双屏、可全屏）？后者要改 `UIDashboardPanel` 的注册方式，成本约 1 天。
2. **值轴缩放手势**：确认按 AE 用 `Alt+滚轮`（会与轨道区的"行高"手势同名但区域互斥）。
   如果你更习惯现在的 `Ctrl+滚轮`，我保留两套并加状态栏提示。
3. **最大关键帧规模**：需要知道实际工程的量级（单通道最多多少键、同时显示几条曲线），
   这决定 P3 的 VBO 是否必要。
4. **30 FPS 是否可接受**：如果 4K 合成 + 15 效果在拖动时只能到 30 FPS，
   是接受"拖动时降分辨率"，还是接受"拖动时降帧"？
5. **批量时间缩放的触发方式**：AE 是 Alt 拖选区边缘；也可以用右键菜单"缩放时间…"输入倍数。
   两者都做还是只做前者？
6. **撤销粒度**：是否接受"图层级快照"（3.7 方案 B）？它改变的是 undo 条目结构，
   不影响工程文件格式，但旧的历史栈不兼容（重启后历史本来就清空，所以实际无影响）。
7. **是否允许改 `CompCurveChannel` 加 `revision` 字段**：这是本轮唯一的数据结构改动，
   不参与序列化、不影响 `.bbscomp` 兼容性。若不允许，退化方案是每帧比较"键数量 + 首末 tick"
   （弱校验，极端情况下会漏失效）。
