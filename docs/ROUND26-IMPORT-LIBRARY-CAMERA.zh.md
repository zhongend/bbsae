## 1. 系统文件对话框

### 1.1 为什么"编译通过"不等于"对话框会出现"

前两版依次用了 tinyfd 和 AWT。两者都是**没有 owner 的原生窗口**：在全屏/无边框的 Minecraft
上，Windows 可以把它放到游戏窗口后面。对话框确实创建了，回调确实没触发，从游戏的角度
**什么都没失败** —— 所以按钮看起来是死的，日志里也没有错误。

第一性原理：**对话框必须被游戏窗口拥有**。Windows 的 owned window 永远在 owner 之上，
这不是"尽量置顶"，而是窗口管理器的不变量。

### 1.2 实现

`Win32FileDialog`：JNA 调 `comdlg32!GetOpenFileNameW`，`hwndOwner` 取
`GLFW.glfwGetWin32Window(handle)`。JNA 是 Minecraft 自带的（BBS 自己的文件夹选择器就在用），
没有新增依赖。结构体按 `OPENFILENAMEW` 逐字段对齐（`LPARAM` 用 `WinBase.LPARAM` 保证 64 位
指针宽度），`lStructSize` 用 `Structure.size()` 而不是硬编码。

三级回退，语义严格区分"取消"与"不可用"：

| 顺序 | 后端 | 返回 null | 抛异常 |
| --- | --- | --- | --- |
| 1 | Win32 owned 对话框 | 用户取消 | 换下一个 |
| 2 | AWT `FileDialog`（非 Windows 的主路径） | 用户取消 | 换下一个 |
| 3 | 游戏内文件浏览器 | — | 只有这一种情况才回退 |

### 1.3 验证方式

不靠"点了应该有反应"：把 `Win32FileDialog` 单独编成一个 `main`，用 `java -cp` 跑起来，
再用 `ffmpeg -f gdigrab` 截桌面 —— 截图里是一张真正的 Windows 打开对话框（标题、过滤器
`*.png;*.jpg`、用户目录都对）。结构体布局错一个字段这里就会崩或显示乱码，所以这一步同时
验证了 ABI。

## 2. 原版音效导入

### 2.1 根因：音效不是路径

`minecraft:block.note_block.bell` 是一个**事件**，它通过 sounds.json 解析到若干 ogg 之一；
`bbs:sounds/...` 则是 BBS 自己资源包里的链接。而合成器的音频轨存的是**工程内相对文件**
（`audio/xxx.ogg`）。旧实现只把 ID 复制到剪贴板，等于什么都没导入 —— 所以"原版音效无法导入"
不是播放坏了，而是**从来没有发生过导入**。

### 2.2 实现

`SoundImport.materialize(id)`：

* 事件 ID → `SoundManager.get(id)`（`WeightedSoundSet`）→ `getSound(Random)` → `getLocation()`，
  再从原版 `ResourceManager` 读字节；
* 显式 `.ogg` 链接 → 先试 BBS 的 `AssetProvider`（`bbs:` 包），再试原版资源；
* 落到临时文件，交给既有的 `addAudioClip` 复制进 `assets/audio` 并建片段。

于是预览、导出、单独 WAV 三条路径读的是同一个文件，没有第二条解码分支。

## 3. 图层库

### 3.1 旧选择器的问题

固定 440×300 的模态、三列一模一样的灰按钮：

* 20 个类型在 300px 高度里放不下，最后一行和"取消"按钮重叠；
* 每个条目只有名字，用户无法判断"调整层"和"空对象"的区别；
* 入口藏在右键菜单里，而"+"按钮直接建了一个纯色层。

### 3.2 新结构

* `LayerCatalog`：id / 名称 / **一句说明** / 分类 / 图标。UI 与渲染器共用这一份数据
  （`LAYER_TYPES` 已删除），`LayerCatalogTest` 保证 id 唯一、分类非空、搜索可用。
* `UILayerLibrary`：搜索框 + 左侧分类 + 卡片网格（图标、名称、分类、说明）+ 添加/取消。
  双击卡片等于点"添加"；Esc 关闭，回车添加。
* 卡片文字按**真实字宽**换行，并且额外用 `clip` 把文字裁在卡片内 —— 中文回退字体的
  advance width 不可靠，只靠测量仍会溢出。
* "+"按钮直接打开图层库；右键菜单里的"添加图层…"进的是同一个地方。

## 4. 真正的 3D 摄像机

### 4.1 根因

摄像机本身早就是 3D 的（位置 + 朝向 + 滚转 + FOV，`view` / `projection` 都在）。
问题在**图层**：非 3D 图层走 `view2D` —— 一个只含平移/缩放/滚转的仿射矩阵。
倾斜相机对它是 no-op，于是"摄像机只能平面移动"。

仿射矩阵**无法**表达透视，这是数学事实，不是实现缺陷。所以要么让 2D 图层走透视，
要么永远得不到 3D。

### 4.2 关键洞察

一个 2D 图层的成品（内容 + 蒙版 + 效果 + 样式）是**一张 comp 空间的图**。这张图代表的
就是 z = 0 平面上的一块平面。既然是平面，它就可以被透视投影 —— 而且投影它不需要重做
任何 pass，只需要把成品图当作一块平面贴上去。

于是：

```
倾斜时（或存在 z ≠ 0 的图层）
  model   = world(layer)                 // 纯 comp 空间，不含相机
  蒙版/效果/样式  照常在 comp 空间完成
  最后    = 把成品图按 z 平面投影一次（camera.view · translate(0,0,z)，camera.projection）
```

直相机（`tilted == false` 且没有 z）仍然走原来的 `view2D` 路径：**零回归、零额外开销**，
这也是为什么现有工程打开后画面一个像素都不变。

排序：空间模式下平坦图层与 3D 图层一起按平面深度排序；同 z 时比较器返回 0，稳定排序保持
堆叠顺序。

### 4.3 手势

* 拖动摄像机本体 = 平移（原有）
* **Alt + 拖动 = 环绕**：眼点绕目标点做球面运动，俯仰夹在 ±85°（到极点时右向量退化，画面会自转）
* 拖动准星 = 重新取景（原有）
* 滚轮 = 推拉，Alt + 滚轮 = 视场（原有）

### 4.4 验证

* `Camera3DTest` 新增三条：直相机不是 tilted 且 `spatial == false`；倾斜后 `spatial == true`
  且平坦图层的 model 不含相机；有 z 的图层也会触发空间路径。
* 实机：倾斜后整幅画面产生真实的透视收缩与视差（截图 `run/screenshots/tilt-cam2`），
  不再是平面平移。
