# Round 23 — 摄像机可用性、3D 叠放与视口稳定性（0.12.0）

> 用户这一轮报的是使用问题，不是理论问题：右键拖不动视角、摄像机图标不显示、3D 里渐变不对、
> BBS 预览层天空变黑、需要运动轨迹、3D 图层叠放不对、首次打开预览与轨道之间有空白、
> 3D 看穿预览播放视频时界面闪烁。每一条都先定位到可证伪的原因，再改。

产物：`bbsae-0.12.0.jar`（676 590 字节，SHA-256
`a86eabec779ed73480757bca5ec766db408f78b5b7e430fa4bb6f6e9f1a3adb7`）。测试 **175/175**。

---

## 1. 右键拖不动视角

第一版只接了中键。中键在笔记本/触控板上根本不存在，所以"视角动不了"是真实的可用性缺陷，
不是用户操作问题。

现在：**右键拖动 = 环绕**，**Shift + 右键 = 平移**，中键保留（Blender 习惯）。
另外，**在看穿摄像机状态下右键拖动会先退出看穿再环绕** —— 这正是 Blender 里"在相机视图里
转动视角就离开相机视图"的行为。

`subMouseClicked` 的分派顺序也因此变了：右键在 3D 空间里永远先被视口消费，不会弹出上下文菜单。

---

## 2. 摄像机图形元素不显示

两个原因：

1. **只画当前激活摄像机**。工程里有第二台摄像机时，它在视口里完全不可见，也就无法选中。
   现在**每一台可见摄像机都有自己的 gizmo**，激活的那台颜色正常，其余压暗。
2. **进入 3D 时的取景只框住合成**。摄像机常常停在合成平面之前/之后很远的地方，取景后落在
   画面外，gizmo 的投影为 null，看起来就是"什么都没有"。

现在的取景策略：**先框住合成（保持画面居中），再只把距离放宽到摄像机也能看见**（最多迭代 10 次）。
不再把"合成 ∪ 摄像机"作为一个包围盒来框 —— 那会把合成推到画面一侧。

---

## 3. 3D 视图里渐变显示不对

原因有两个，而且是叠加的：

### 3.1 预乘 alpha 用直通混合画（所有半透明像素都变暗）

BBS 把直通 alpha 的图元用 `SRC_ALPHA` 画到透明目标上，结果天然是**预乘**的。
源纹理缓存最初直接把这个纹理按直通 alpha 混合画到视口，于是越透明的地方越暗：
渐变填充发灰、BBS 预览层的天空直接变黑。

修复：源纹理在**构建时**做一次 unpremultiply（全屏 pass，不是每帧），之后所有消费者用普通混合。
这也顺带修掉了第 4 条的一半。

### 3.2 效果完全没有参与草稿

草稿之前按设计跳过效果，于是"用 gradient_ramp 做的渐变卡片"在 3D 里是纯白的。

现在效果**烘焙进图层本地纹理**：`CompLayerSourceCache.applyEffects` 用
`EffectSpace.ofBounds(layer, world, ctx, rect…)` 显式给出"本地像素 → 栅格像素"的映射，
代理合成的尺寸就是栅格尺寸。这样渐变锚在**图层自己的矩形**上，转动视角不会在四边形上滑动。
（合成管线里 3D 图层用合成空间的 EffectSpace，是因为它在合成空间里栅格化；两份映射各自正确。）

跳过：`depth_*`（需要世界深度缓冲）、`shake`（是变换不是像素 pass）。
蒙版/轨道遮罩/混合模式仍然不参与草稿 —— 它们是对"已合成画面"的操作。

**代价**：效果只在内容变化时重算一次（缓存指纹），转视角/拖图层仍然是 0 次。

## 4. BBS 预览图层的天空是黑的

世界帧是 `glCopyTexSubImage2D` 从主 framebuffer 拷来的。主 framebuffer 的 **alpha 通道没有语义**
（天空处没有混合任何东西，alpha 常常是 0），而 `drawBbsPreview` 之前把这个 alpha 当透明度用，
天空就变成了"透明 → 露出黑色舞台"。

修复：**世界帧按不透明处理**（tint 强制 `| 0xFF000000`）。一帧影片本来就没有透明通道。

---

## 5. 摄像机运动轨迹预览

激活摄像机的运动轨迹直接**采样 `CompCamera.eyeOf()`**（和渲染同一个函数），
在视口里画成 40 段折线 + 每个 transform 关键帧一个点：

* 轨迹是"读"动画，不是另存一份路径，因此永远不会和实拍不一致；
* 选中摄像机时高亮，未选中时压暗（不抢画面）；
* 40 段是有意的上限：它每帧都画，而人眼读不出更细的折线。

## 6. 3D 图层叠放

旧的排序键是图层**原点**的相机空间深度，或（我上一轮改的）**最近角点**深度。两者都不对：

* 原点：同样在 z=0 的两层，倾斜视角下原点深度不同 → 大背景层会盖住上面的小层；
* 最近角点：大平面的下边缘离相机更近 → 同样会盖住。

正确的问题是"**这两个平面哪个在前面**"，答案与图层在画面里的位置无关。所以排序键改成
**平面深度**：

```
t = dot(origin - eye, n) / dot(f, n)      // n = 图层世界 Z 轴，f = 相机前向
planeDepth = -t                            // 相机空间 z，越远越负
```

* 共面图层（绝大多数，z 都为 0）**严格相等** → 由堆栈顺序决定，和合成器一致；
* z = +180 的图层从任何角度都排在前；
* 边缘视角（`dot(n,f) ≈ 0`）回退到原点深度。

`CompRenderer.sortSegment`（成片里的 3D 槽位排序）也换成了同一个键：
**预览里的前后关系和导出必须一致**。

## 7. 首次打开时预览与轨道之间有一条空白

`applyLayout()` 只在 `bind()` 时跑一次，那时 dashboard 还没给面板真实尺寸，
`body` 用的是 160px 下限，而时间轴是贴底的 → 中间留出一条空白。拖动分栏会重新布局，所以"拖一下就好了"。

修复：面板 `render()` 里比较 `area` 尺寸，变了就重跑 `applyLayout()`。
这条也顺带修掉了窗口缩放/全屏切换后的同类错位。

## 8. 看穿预览播放视频时界面闪烁

三个真实原因，逐个消除：

1. **UI 的顶点被画进了 3D 的 FBO**。场景 pass 和 UI 共用 Minecraft 的 immediate 顶点缓冲；
   在绑定场景 FBO 之后再 flush，会把本帧已经排队的 UI 顶点画进 3D 纹理里，下一帧又重新排一次 →
   交替闪烁。现在在绑定场景 FBO **之前**先 flush 面板批次。
2. **每帧申请/归还场景 FBO**。改成持有一个持久目标（尺寸变化才换），不再进池子；
   也因此不能再 `release` 它（否则下一层会拿到正在被采样的纹理）。
3. **动画图层的源纹理每帧重新分配**。footage/动画文字每帧内容都变，原来每帧两对 FBO 进出池子，
   池子长期在极限上。现在缓存项持有 **staging + straight 两个目标**，同尺寸时**原地重绘**，
   播放期间分配次数为 0（带效果的图层仍然走分配路径，因为效果 pass 自己会开目标）。
4. **指纹里无条件混入了帧号**。这让每一层（包括纯色、图片、静态文字）在播放时**每帧都重建**。
   现在只有当图层"内容确实随时间变化"时才把帧号计入指纹：footage、文字动画器、
   或存在 `text/` `shape/` `fx/` 关键帧通道。静态图层播放时重建次数 **0**。

### 8.1 追这个闪烁时抓到的真 bug：FBO 双重释放

加上 `FboPool` 的重复释放守卫后，日志直接给出了答案：

```
FboPool: double release of framebuffer 18 (520x320)
  at CompLayerSourceCache.rasterize(CompLayerSourceCache.java:312)
```

`applyEffects` 在效果 pass 产生新目标时**自己释放了输入**，而调用方又释放了一次 `straight`。
同一个 framebuffer 进了池子两次 → 两个消费者渲染进同一张纹理 → 画面撕裂/闪烁，
而且**没有任何 GL 错误**（第一次跑就是这样，只有 "texture is not the name of an existing texture"
这类间接症状）。

现在 `FboPool.release` 永久带守卫：重复释放会被拒绝并打一条 warning（`-Dbbsae.debugFbo=true`
时附堆栈）。这不是临时探针，是池子的不变量。
